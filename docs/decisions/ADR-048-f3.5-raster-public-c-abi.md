# ADR-048: F3.5 — Raster Reaches the Public C-ABI

Status: Accepted

## Context

F2 (ADR-046) made rasterization a shape of `core::TaskRecord`/
`ExecutionPlan`, and F3 (ADR-047) let a caller supply hand-written MSL
vertex/fragment logic through the restricted-import `CodeObject` path — but
both milestones were explicitly scoped as C++-internal. ADR-046's
Consequences said so directly: "No public C-ABI (`include/vg/vg.h`'s
`VgTaskRecord`) changes -- F2 is fully internal to C++; a public raster ABI
entry point is deferred to a later F milestone." Every raster test built
before this ADR (`tests/unit/reference_raster_test.cpp`,
`tests/vertical_slice/metal_task_timeline_test.cpp`,
`tests/vertical_slice/vulkan_task_timeline_test.cpp`) called
`DeviceHal::run_raster_triangles`/`TaskGraphBuilder::append` directly against
`core::TaskRecord`, never through `include/vg/vg.h`.

This surfaced as a concrete gap, not a speculative one, when the user asked
for a genuine end-to-end test of F3 driven through the real public C-ABI —
the same kind of test `api.c-abi-conformance`
(`tests/api/vg_c_abi_conformance_test.cpp`, introduced by ADR-044) already
gives F1. That test is impossible to write today: `VgTaskRecord`
(`include/vg/vg.h`) has no `kind`/`topology`/`raster_facets`/
`vertex_buffer_ref`/`index_buffer_ref` fields to request a raster task with,
and `VgApi` has no entry point that returns a `VgFacetRef` a caller could
even put in those fields if they existed — `acquireFacet` did not exist.
`getAllocationRef` (v1.1) is the closest existing analog, and it returns an
`id`/`generation` pair, not a facet.

ADR-043's own Phase F milestone list (`docs/decisions/
ADR-043-phase-f-raster-sdk-scope-and-abi-expansion.md`, §9: "F0 (this ADR) →
F1 (C ABI expansion) → F2 (raster as a Task shape) → F3 (restricted shader
import) → F4 (depth + real PSO) → F5 (index buffers) → ... → F10 (BGRA8
drawable format)") does not name this gap at all — F3.5 sits, previously
unnamed, between F3 and F4. This ADR is filling a hole ADR-043 didn't
anticipate, not reopening or redoing settled F2/F3 scope.

## Decision

**1. `VgTaskRecord` grows by plain trailing-field append — no
`VgStructHeader` retrofit, no sentinel tag.** `04-public-c-abi.md` §5 states
a general rule for every other struct in this ABI: "不允许通过在普通
struct 尾部盲加字段破坏 ABI" ("blindly appending fields to the tail of an
ordinary struct, breaking the ABI, is not allowed"). `VgTaskRecord`'s growth
here is not that: it is disclosed and cited, not blind — the same
reconciliation ADR-044 already used once for `root_generation`. §17
separately, and explicitly, licenses this move for exactly this struct: the
example's descriptor fields are stated to be illustrative, "具体
descriptor 字段可随 ADR 调整" ("illustrative struct fields can be adjusted
per ADR"), and ADR-044 already exercised that license — adding
`root_generation` to carry `core::TaskRecord`'s split identity that the
illustrative bare `uint64_t root` had no room for. `include/vg/vg.h`'s
current `VgTaskRecord` doc comment cites that exact precedent verbatim
("Recompile hazard (ADR-048, precedented by root_generation's addition
above under ADR-044)"). This ADR repeats the same move a second time,
appending `kind`, `topology`, `raster_facets`, `vertex_buffer_ref`,
`index_buffer_ref`, `index_count`, `raster_filter`, `raster_wrap`,
`raster_tint` after the v1.1 fields — cited here, disclosed in the header's
own doc comment, and covered by this ADR's Evidence section, which is what
keeps it from being the "blind" append §5 rules out.

The recompile hazard is disclosed explicitly in `vg.h`'s doc comment on
`VgTaskRecord`, not left implicit: unlike every other struct in the header,
`VgTaskRecord` carries no per-element `VgStructHeader` and is passed to
`taskGraphAppend` as a raw array — there is no runtime size negotiation for
it the way `VgApi` negotiates `size` once per `vgGetApi` call. Appending
these fields changes `sizeof(VgTaskRecord)`; an application binary compiled
against an older, smaller header but run against a newer `libvg` will have
`taskGraphAppend`'s array indexing computed from the *library's* larger
compiled-in `sizeof`, reading past the end of the caller's own array — an
out-of-bounds read for a stale-header caller. This is why the doc comment is
explicit that callers **must** recompile against the current header when
linking against a `libvg` built from this version; §16's "old header + new
runtime" compatibility test class does not, and cannot, cover
`VgTaskRecord`'s raw-array growth the way it covers `VgApi`'s `size`-gated
growth.

A `VgStructHeader` retrofit onto `VgTaskRecord` was rejected: `VgTaskRecord`
is a hot-path, batch-appended array element by design (`taskGraphAppend`
takes `const VgTaskRecord* tasks, uint32_t task_count`) — giving every
element its own 16-byte `{type, size, next}` header would be a real per-task
overhead and a real layout change to every existing caller, to guard against
a hazard that recompilation already fully closes. A sentinel-tag mitigation
(e.g. a magic value at a fixed offset that `taskGraphAppend` checks before
trusting the rest of the record) was also rejected: it doesn't catch the
actual failure mode. The stride-mismatch happens in `task_graph_append`'s
own array indexing (`tasks[i]`, computed from the library's compiled-in
`sizeof(VgTaskRecord)`) *before* any field of that mis-strided element,
sentinel included, is ever read — the pointer arithmetic itself is already
wrong by the time a sentinel check would run, so a sentinel could not
observe the mismatch it exists to catch.

**2. New `VgCanonicalViewDesc` (header-bearing) and `VgRasterFacetPair`
(plain), mirroring `core::CanonicalView`/`core::RasterFacetPair`
field-for-field.** `VgCanonicalViewDesc` gets a `VgStructHeader` — unlike
`VgTaskRecord`, it is a one-shot `acquireFacet` input, not a hot-path array
element, so the standard extensible-struct convention (`04-public-c-abi.md`
§5) applies with none of Decision #1's batch-overhead objection.
`VgRasterFacetPair` (embedded inside `VgTaskRecord` as `raster_facets`)
stays a plain, header-less pair of `VgFacetRef`, matching
`core::RasterFacetPair`'s own plain-struct shape and `VgTaskRecord`'s own
no-header discipline for anything nested inside it.

`VgCanonicalViewDesc::allocation`/`allocation_generation` are a raw
`uint64_t id` / `uint32_t generation` pair, not a `VgAllocation` handle —
this matches `core::CanonicalView`'s own field type (`uint64_t allocation;
uint32_t allocation_generation;`, `src/core/core.h`) exactly, and reuses the
existing `getAllocationRef(VgAllocation, uint64_t*, uint32_t*)` v1.1 entry
point as the only way to produce that pair, rather than inventing a second,
parallel handle-to-id-pair mechanism just for this struct.

**3. New `acquireFacet` v1.3 entry point, backend-agnostic.**
`VgResult acquireFacet(VgDevice device, VgArena arena, const
VgCanonicalViewDesc* view, uint32_t facet_kind, VgFacetRef* out_facet)` is
the public entry point onto `core::FacetPool::acquire`, letting a caller
obtain the `VgFacetRef` a `VG_TASK_KIND_RASTER` `VgTaskRecord`'s
`raster_facets`/`vertex_buffer_ref`/`index_buffer_ref` fields require. It is
reached through `facet_pool()`, a member `hal::DeviceHal` already exposes on
its shared base (`core::FacetPool& facet_pool()` /
`const core::FacetPool& facet_pool() const`, `src/backends/device_hal.h`) —
identical across reference/Metal/Vulkan, so `acquireFacet`'s implementation
needs no per-backend dispatch at all. This is unlike F3 (ADR-047), which
forked per-backend (`reference_device_hal.cpp` and `metal_device_hal.mm`
each independently recording the `HostAssisted` event and handling
`user_raster_shader`) because restricted-import shading is genuinely
backend-specific machinery; facet acquisition already was not.

`VgApi`'s v1.0→v1.1→v1.2→v1.3 append-only, `size`-gated version-negotiation
discipline (ADR-044, reused unmodified by ADR-045 for v1.2) is extended a
third time: `acquireFacet` is appended strictly after
`getSubmissionExecutionResult`, and `vgGetApi` gains a fourth `size`
boundary (`v1_2_size` → `full_size` for v1.3) following the exact pattern
`vg_api.cpp`'s existing `v1_0_size`/`v1_1_size`/`v1_2_size` cascade already
establishes.

**4. The `raster_filter`/`raster_tint` zero-init defaulting mismatch is
caller responsibility, not fixed with default-substitution logic in
`task_graph_append`.** A zero-initialized `VgTaskRecord` correctly decodes
`kind = VG_TASK_KIND_COMPUTE`, `topology = VG_TOPOLOGY_TRIANGLE_LIST`, and
`raster_wrap = VG_WRAP_CLAMP` (all ordinal 0, matching
`core::TaskRecord`'s real in-memory defaults), but does **not** correctly
default `raster_filter` (zero decodes as `VG_FILTER_NEAREST`, while
`core::TaskRecord::raster_filter`'s actual default is
`FilterMode::Bilinear`, ordinal 1) or `raster_tint` (zero decodes as
`{0,0,0,0}`, while the internal default is `{1,1,1,1}`, opaque white). This
mismatch exists because `TaskKind`/`Topology`/`WrapMode` all happen to have
their intended default as enumerator 0, while `FilterMode::Bilinear` (the
intended default) is enumerator 1 and `raster_tint`'s intended default is a
non-zero value no C zero-initialization can express.

`task_graph_append` copies every v1.3 field through as-is — no
default-substitution branch that would, say, rewrite a zero `raster_filter`
to `VG_FILTER_BILINEAR` before constructing `core::TaskRecord`. Two reasons:
first, correctness — backends never read `raster_filter`/`raster_tint` for
a `VG_TASK_KIND_COMPUTE` task at all, so a blind field-by-field copy is
already exactly right for the common (compute) case, and a
default-substitution branch would have to condition on `kind`, adding
branching to `task_graph_append`'s hot append path for a case that only
matters when `kind == VG_TASK_KIND_RASTER`. Second, semantics — a
zero-initialized `VG_TASK_KIND_RASTER` task is caller error, not an
ambiguous input the API should paper over: `vg.h`'s `VgTaskRecord` doc
comment states this directly, "a caller submitting a VG_TASK_KIND_RASTER
task must explicitly set raster_filter and raster_tint rather than relying
on zero-init." Silently substituting a different value than what the caller
wrote (even a well-intentioned one) would be exactly the kind of implicit
behavior `04-public-c-abi.md` §1's design goals and `docs/START.md` §4's
"no silent degradation" invariant rule out elsewhere in this ABI; the
correct fix is documented zero-init semantics, which is what this ADR and
the header comment together provide.

## Implementation

This ADR's decisions are fully reflected in `include/vg/vg.h` (Agent 1's
completed, verified work): the v1.3 `VgTaskRecord` field block, the new
`VgCanonicalViewDesc`/`VgRasterFacetPair` structs, the `VG_TASK_KIND_*`/
`VG_TOPOLOGY_*`/`VG_FILTER_*`/`VG_WRAP_*`/`VG_PIXEL_FORMAT_*`/
`VG_VIEW_DIMENSION_*`/`VG_SWIZZLE_*`/`VG_STRUCTURE_CANONICAL_VIEW_DESC` enum
blocks, the `acquireFacet` function-pointer member, and
`include/vg/vg_version.h`'s `VG_API_VERSION_1_3`/`VG_HEADER_VERSION_1_3 =
0x00010003u`.

The C-ABI plumbing layer (`src/api/*.cpp`, `CMakeLists.txt`) was implemented
concurrently by a separate work stream; it is landed in the working tree
(confirmed via `git status`/`git diff`) and is now exercised end-to-end by
Agent 3's test, with the full ctest results confirmed independently (see
Evidence below). It touches: `src/api/vg_api.cpp` (the `vgGetApi`
version/size-boundary cascade gains a v1.3 tier — `offsetof(VgApi,
acquireFacet)` is the v1.2 boundary, `sizeof(VgApi)` the v1.3 one — and the
function table wires `acquireFacet` to `vg_api::acquire_facet`);
`src/api/vg_api_taskgraph.cpp` (`task_graph_append`'s existing field-by-field
`VgTaskRecord` → `core::TaskRecord` copy is extended to the v1.3 fields,
explicitly commented as no-default-substitution, matching Decision #4);
`src/api/vg_api_facet.cpp` (a new file implementing `acquire_facet`:
translates `VgCanonicalViewDesc` to `core::CanonicalView` field-for-field and
calls `device->hal->facet_pool().acquire(...)` against the given `VgArena`'s
`core::Arena`, per Decision #3); `src/api/vg_api_internal.h` (the
`acquire_facet` declaration); and `CMakeLists.txt` (registers
`src/api/vg_api_facet.cpp` as a build source). This section intentionally
does not cite specific line numbers for that layer, since it was still
in-flight, uncommitted work at the time this ADR was drafted and may still
change before Agent 3's test and the associated ctest run land.

## Alternatives

- **`VgStructHeader` retrofit onto `VgTaskRecord`**: rejected — see Decision
  #1. Would add real per-element overhead to a deliberately hot-path,
  header-less, batch-appended array element, to guard against a hazard that
  mandatory recompilation already fully closes.
- **Sentinel/magic-value tag mitigation for the recompile hazard**: rejected
  — see Decision #1. Does not catch the actual failure mode: the
  stride-mismatch happens in `task_graph_append`'s own pointer arithmetic
  before any field of a mis-strided element — sentinel included — is ever
  read.
- **`VgAllocation` handle instead of raw id/generation on
  `VgCanonicalViewDesc`**: rejected — see Decision #2. Would not match
  `core::CanonicalView`'s actual field type and would require either a new
  handle-to-id-pair translation inside `acquireFacet`'s implementation or a
  second, parallel mechanism alongside the existing
  `getAllocationRef`/`allocation`+`allocation_generation` pattern F1
  already established.
- **Per-backend `acquireFacet` implementation** (mirroring F3's
  reference/Metal split): rejected — see Decision #3. `facet_pool()` is
  already identical across all three `DeviceHal` backends; forking the
  implementation would add maintenance surface with no corresponding
  behavioral difference to express.
- **Default-substitution for zero-initialized `raster_filter`/`raster_tint`
  in `task_graph_append`**: rejected — see Decision #4. Correct only for
  `VG_TASK_KIND_RASTER` tasks, so it would require branching on `kind` in a
  hot append path, and it silently substitutes a value the caller never
  wrote — exactly the kind of implicit behavior this ABI's design goals and
  `docs/START.md` §4's no-silent-degradation invariant rule out elsewhere.

## Consequences

- Unblocks the genuine end-to-end public-C-ABI raster test the user asked
  for: a caller can now build a `VG_TASK_KIND_RASTER` `VgTaskRecord`,
  acquire its `VgFacetRef`s via the new `acquireFacet`, and submit it —
  entirely through `include/vg/vg.h`, without touching `vg_core`/
  `vg_backend_reference`/`vg_backend_metal` directly. This closes the gap
  ADR-046's Consequences explicitly deferred ("a public raster ABI entry
  point is deferred to a later F milestone").
- `VgApi` is now versioned `0x00010003` (`VG_API_VERSION_1_3`);
  `vgGetApi(VG_API_VERSION_1_0/1_1/1_2, ...)` remain supported and
  byte-identical to their pre-F3.5 contracts, per the same append-only,
  `size`-gated discipline ADR-044/ADR-045 established.
- Restricted-import MSL shading (F3/ADR-047) is not itself re-exposed by
  this ADR beyond what `loadCodeObject`'s existing `format_tag` mechanism
  already allowed (no C-ABI version bump was needed for F3 itself) — F3.5
  only adds the ability to *submit* a raster task and acquire its facets
  through the public ABI; the `"vg.msl.raster/v1"` envelope path is reached
  the same way F3 left it, through `loadCodeObject`.
- Still explicitly out of scope, unchanged from F3/ADR-047's own scope cuts
  (not reopened here): mixed compute+raster in one submission
  (`ExecutionPlan::validate()` still rejects a `user_raster_shader`
  submission containing a non-`Raster` task); indexed raster draws
  (`index_count > 0` is still rejected at `compile()` time, deferred to F5);
  depth (F4); per-shader declarable bindings (still fixed, per ADR-047
  Decision #3).
- The recompile hazard (Decision #1) and the zero-init defaulting mismatch
  (Decision #4) are both now load-bearing, disclosed constraints on every
  future caller of `VgTaskRecord`/`taskGraphAppend` — not just an
  implementation detail of this milestone.
- Two further disclosed API-surface gaps surfaced while writing the
  end-to-end test (Evidence below), not bugs but real v1.0–v1.3 absences:
  (Gap #1) no public write-to-allocation entry point exists anywhere in
  v1.0–v1.3, so the vertex/texture allocations a caller acquires facets
  against are necessarily zero-filled unless populated some other way; (Gap
  #2) no public pixel-readback entry point exists, so true pixel-level
  correctness cannot be asserted through the pure public C-ABI alone — the
  new test instead uses a differential proof (a correct vs. a deliberately
  wrong `fragment_entry` name) to demonstrate that real MSL compilation is
  genuinely driven by caller-supplied text, without being able to read back
  and compare actual pixels. Both are scope gaps for a future milestone to
  close, not defects in this one.

## Evidence

Agent 3's end-to-end C-ABI raster test has landed and been independently
verified (not merely relayed from Agent 3's own report). The change is
scoped to a single file: `tests/api/vg_c_abi_conformance_test.cpp` (+665/-0
lines) — the existing `api.c-abi-conformance` binary/ctest target
(introduced by ADR-044) is extended in place; no new ctest target was
registered.

The new coverage added to that file:

- **Golden-path end-to-end raster submission.** Entirely through
  `include/vg/vg.h`: `vgGetApi` requesting `VG_API_VERSION_1_3` →
  `createRuntime`/`openAdapter`/`createDevice`/`createArena` →
  `loadCodeObject` with `format_tag = "vg.msl.raster/v1"` → `acquireFacet`
  with `source = Sample`, `target = Attachment`, `vertex = Address` →
  `createNode`/`createTaskGraphBuilder` → `taskGraphAppend` with a
  `VG_TASK_KIND_RASTER` `VgTaskRecord` → `sealTaskGraph` → `submit` →
  `getSubmissionExecutionResult`, asserting `"ok": 1` in the canonical JSON
  result.
- **Sub-case (b), Metal-only: malformed `fragment_entry`.** The JSON
  envelope declares a `fragment_entry` name absent from the compiled MSL
  source. `submit()` itself still returns `VG_SUCCESS` (host-side
  acceptance), but `getSubmissionExecutionResult` reports `"ok": 0` with a
  message containing `"Metal raster pipeline compile failed"` — proving the
  entry-name string genuinely drives Metal's function lookup at pipeline
  build time, not just JSON parsing.
- **Sub-case (c), backend-agnostic: mixed compute+raster rejection.** A
  mixed `[VG_TASK_KIND_COMPUTE, VG_TASK_KIND_RASTER]` task array submitted
  under a `user_raster_shader` code object: `taskGraphAppend` succeeds, but
  `submit()` returns `VG_ERROR_INVALID_ARGUMENT`.
- **v1.3 version-skew regression case.** `vgGetApi(VG_API_VERSION_1_2, ...)`
  called against the v1.3 library asserts the returned `size` equals
  `offsetof(VgApi, acquireFacet)` — confirming the append-only, `size`-gated
  discipline (Decision #3) holds for an older-version caller against the
  newer library.
- **Two disclosed API-surface gaps, documented in the test itself, not
  silently worked around:** (Gap #1) no public write-to-allocation entry
  point exists anywhere in v1.0–v1.3, so the vertex/texture allocations the
  test acquires facets against are necessarily zero-filled; (Gap #2) no
  public pixel-readback entry point exists, so the test cannot assert
  pixel-level correctness through the pure public C-ABI — it instead relies
  on the differential proof in sub-case (b) (good vs. deliberately-wrong
  `fragment_entry`) to demonstrate genuine MSL compilation.

Build and test results, independently confirmed via force-rebuild (deleted
each target's `CMakeFiles` `.dir` subdirectory first, so nothing was served
from stale object files) followed by `ctest`:

- `build/dev-reference`: clean build succeeded; `ctest` reports 100% tests
  passed, 0 failed — **26/26**.
- `build/dev-metal`: clean build succeeded; `ctest` reports 100% tests
  passed, 0 failed — **56/56**.
- Both `vg_c_abi_conformance_test` binaries were additionally run directly
  (not just through `ctest`); both exited 0 on reference and Metal. Given
  the test file's own `check()`/`g_ok` pattern (`check()` sets `g_ok = false`
  on any failed assertion; `main` returns `g_ok ? 0 : 1`), an exit code of 0
  on both backends confirms every assertion in the new raster block —
  golden path, sub-case (b), sub-case (c), and the version-skew case —
  passed on both.

## Revisit trigger

Revisit the plain-append growth strategy for `VgTaskRecord` if it needs to
grow a third time (past this ADR's v1.3 addition), or if a real caller
reports an actual out-of-bounds-read incident traced to stale
recompilation against an older header — at which point a versioned/
negotiated struct layout (or the `VgStructHeader` retrofit rejected in this
ADR's Alternatives) should be reconsidered rather than assumed still
inapplicable. Also revisit if a future milestone needs `VgCanonicalViewDesc`
to describe a shape `core::CanonicalView` itself doesn't yet have (e.g. a
new `PixelFormat`/`ViewDimension` enumerator) — the mirrored-field-for-field
convention this ADR establishes should stay the reference shape both sides
are kept in sync against, not silently diverge.
